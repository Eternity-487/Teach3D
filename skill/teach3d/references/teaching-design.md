## Lesson contract

Start from what the learner should explain after operating the model. Limit a short lesson to three or four measurable objectives. Map every objective to a visible model state, not only to explanatory text.

Useful objective verbs: identify, compare, trace, explain, predict, justify. Avoid vague verbs such as understand or learn unless a student response makes them observable.

## Step pattern

Each guided step uses four fields:

1. `Action`: one clear model operation.
2. `Observation`: what changes or becomes visible.
3. `Question`: a prompt that requires interpretation.
4. `Evidence`: what a satisfactory student response contains.

Keep the action possible within the current interface. Do not ask learners to observe an internal process that the model does not visualize.

For a short classroom introduction, use this sequence:

- whole → parts;
- parts → connections;
- connections → process;
- process → application or prediction.

## Public repository copy

Put these items above long technical details:

- project promise in one sentence;
- `中文 | English` links;
- live demo button;
- real screenshot;
- install command;
- one invocation example;
- three representative use cases.

Use the first finished model as a showcase, not as the project definition. For example, label a bicycle “Mechanical systems example” and leave room for anatomy, laboratory apparatus, architecture, geography, or historical objects.

## Accuracy boundaries

Categorize claims:

- `verified`: supported by an authoritative source or user-provided measurement;
- `estimated`: derived visually and labeled as approximate;
- `illustrative`: simplified to teach a relationship;
- `unknown`: hidden or unsupported and not invented.

Public lessons should show a short boundary note near the model and retain detailed provenance in the lesson spec.
